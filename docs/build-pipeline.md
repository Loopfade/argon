# Полная сборка одним ручным запуском

В GitHub Actions выберите **Сборка Argon (полный цикл)** → **Run workflow**
и ветку **main**. Файл точки входа — `.github/workflows/build-all.yml`.

Для полной сборки **без публикации APK в Releases** выберите отдельный
**Сборка Argon (только артефакты)** → **Run workflow** → **main**
(`.github/workflows/build-all-no-publish.yml`). Проверка необходимости этапов,
Docker-образ, параллельные ARM/ARM64, кеш, подпись, проверка APK и автопродолжение
работают так же. Оба APK доступны в **Artifacts** запуска 30 дней, включая
`signing: Релизная`: здесь этот параметр выбирает постоянный ключ подписи,
а релиз не создаётся. `signing: Тестовая` использует временный ключ, как и раньше.
Проверенные APK с совпадающими входами могут переиспользоваться между обоими
workflow. Они используют общую очередь сборки одной ветки.

Параметры запуска:

| Параметр | Назначение |
| --- | --- |
| `signing: Релизная` | Проверка постоянного ключа, сборка двух ARM APK и публикация проверенного релиза |
| `signing: Тестовая` | Временная тестовая подпись; APK доступны в артефактах запуска |
| `runner` | Linux x64 runner для компиляции, минимум 100 GiB свободного места |
| `auto_continue` | Продолжать тот же цикл после исчерпания времени runner; по умолчанию включено |

Новый цикл запускается вручную. Push и pull request выполняют `validate.yml`,
без сборки APK и публикации prepared image. При несовпадении подготовленных
входов validation создаёт временный Chromium checkout внутри BuildKit;
проверяет полные GN-графы обеих ABI, цели JNI/Java/APK и нативные domain tests.
Результат не заменяет общий образ `branch-main`.
Прежние `build.yml` и `build-arch.yml` удалены. Подготовка образа, сборка
архитектуры и публикация доступны конвейеру через `workflow_call`.

## Как выбирается необходимая работа

1. Проверяются закреплённые входы обеих архитектур. Для release до дорогих
   этапов проверяются PKCS12, пароли, alias и действительность сертификата.
2. Для ARM64 и ARM независимо ищутся доступные артефакты предыдущих запусков
   обоих полных workflow. Совпасть должны коммит, архитектура, режим подписи,
   отпечаток подготовленных входов и release-сертификат. APK заново проверяется
   через SHA-256, apksigner, zipalign, aapt2 и проверку ABI. Проверенные файлы
   прикрепляются к текущему запуску с исходными сведениями о сборке.
3. Если оба APK переиспользованы, Docker и компиляция пропускаются. Иначе
   проверяется manifest/config образа `ghcr.io/loopfade/argon-build:branch-main`
   без скачивания слоёв Chromium. Метка `io.argon.prepared-inputs` содержит
   отпечаток исходников, патчей и рецепта подготовки. При совпадении используется
   существующий образ, при несовпадении выполняется Docker-сборка с BuildKit cache.
4. Полученный immutable digest один раз передаётся всем недостающим сборкам.
   ARM и ARM64 компилируются параллельно, если нужны обе архитектуры.
   При `TOOMANYREQUESTS` от GHCR скачивание повторяется до четырёх попыток
   с паузами 10/20/40 секунд и учётом `retry-after` до 60 секунд. Все попытки
   используют тот же digest; ошибки доступа, отсутствующий образ и заполненный
   диск сразу останавливают задачу. Такое же правило применяется в проверках.
5. Восстанавливается ccache своей версии/ревизии Chromium и архитектуры.
   Новая версия Chromium начинает отдельный чистый кеш. Изменения Argon внутри
   той же версии используют накопленные результаты.
6. Ninja запускается один раз и выполняет недостающие цели, включая JNI,
   Java и APK. Отдельного обязательного прогрева перед сборкой нет.
   Подпись, проверка APK и запись сведений о его происхождении выполняются
   внутри одного контейнера, чтобы работать с файлами от того же пользователя.
7. Для release существующий издатель проверяет оба APK и публикует релиз;
   повторная публикация тех же файлов использует его проверки идемпотентности.

Сводка запуска показывает, какие APK и образ переиспользованы. Сводка каждой
компилируемой архитектуры содержит результат и ключ восстановленного кеша;
журнал содержит статистику ccache.

Карта системных C++-модулей Android использует общий каталог заголовков NDK
и каталог только целевой архитектуры. Выбор принудительных `asm/*`-заголовков
не зависит от порядка обхода каталогов других архитектур. Исправление применяется
в слое патчей prepared-образа, сохраняя слой исходников, SDK и компилятора.
Ключ ccache не меняется: уже сохранённые результаты с такой же картой подходят,
а записи только с прежней картой потребуют однократной перекомпиляции.

Для исследования промахов есть ручной workflow **Проверка кеша компиляции ARM**.
Выбор `arm` или `arm64` восстанавливает отдельный кеш этой архитектуры для
версии и ревизии из текущего `build-lock.json`. Диагностика сравнивает хеши
зависимостей в манифестах и заголовки сохранённых Clang-модулей. Результаты
распаковываются во временные каталоги; workflow не сохраняет и не удаляет кеш.

## Сохранение прогресса и продолжение

Пока Ninja работает, приблизительно раз в час сохраняется отдельный снимок
ccache. Архивируется снимок, а компилятор продолжает работать со своим живым
каталогом кеша. Эти сохранения не прерывают Java-задачи или линковку.

После каждого часового ожидания checkpoint выводит подробную статистику
живого кеша через `ccache --show-stats --verbose`: попадания, промахи, размер,
ошибки и некешируемые вызовы. Счётчики накапливаются после сброса перед началом
сборки. Вывод выполняется и при завершении сборки до конца часа; ошибка
диагностической команды не блокирует сохранение снимка.

Перед шестичасовым дедлайном сборка контролируемо останавливается с резервом
30 минут на финальный снимок и загрузку артефактов; дополнительно оставляется
три минуты на остановку процессов. Незавершённые линковка и Java-задачи между
разными runner не сохраняются, поэтому они получают непрерывное время в каждой
попытке. Каталог `out` не переносится между runner.

Автопродолжение разрешается только после фактического исчерпания бюджета и
подтверждения нового непустого снимка через GitHub API. Оно повторяет нужные
неуспешные архитектуры исходного запуска с прежним коммитом и digest образа.
Успешная архитектура повторно не собирается. Ошибки компиляции, подписи,
проверки происхождения и ранний OOM не запускают автопродолжение. Число
автоматических продолжений ограничено десятью.

Если `auto_continue` выключено, повторить незавершённую работу можно через
**Re-run failed jobs**: накопленный ccache восстановится. Отменённые пользователем
запуски автоматически не продолжаются.

Внутри одной версии и ревизии Chromium старые снимки удаляются после
подтверждённого сохранения нового. При переходе на новую версию перед
восстановлением отдельно удаляются кеши старых версий этой ABI в той же
ветке: они не подходят новому компилятору и освобождают место для прогресса
новой сборки. Кеши другой ABI, другой ветки и более новой версии сохраняются.
Старые версии prepared-образа очищаются после завершения потребителей;
активные сборки и проверки сохраняют используемые digest.

Первый запуск после перехода со старой схемы может обновить образ: старый
образ не содержит метки отпечатка. При этом существующий BuildKit cache и
ccache той же версии Chromium продолжают использоваться. APK старых workflow
без метаданных нового плана не считаются готовым результатом полного workflow.
