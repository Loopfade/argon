# Полная сборка одним ручным запуском

В GitHub Actions выберите **Сборка Argon (полный цикл)** → **Run workflow**
и ветку **main**. Файл точки входа — `.github/workflows/build-all.yml`.

Для полной сборки **без публикации APK в Releases** выберите отдельный
**Сборка Argon (только артефакты)** → **Run workflow** → **main**
(`.github/workflows/build-all-no-publish.yml`). Проверка необходимости этапов,
Docker-образ, параллельные ARM/ARM64, кеш, подпись, проверка APK и автопродолжение
работают так же. Оба APK доступны в **Artifacts** запуска 30 дней, включая
`signing: Релизная`: здесь этот параметр выбирает постоянный ключ подписи,
а релиз не создаётся. `signing: Тестовая` использует временный ключ, как и раньше.
Проверенные APK с совпадающими входами могут переиспользоваться между обоими
workflow. Они используют общую очередь сборки одной ветки.

## Проверка временной ветки перед слиянием

Для цикла **один PR → тестовая сборка его ветки → слияние → сборка main**
есть новый workflow **Тестовая сборка Argon из временной ветки**
(`.github/workflows/build-test-branch.yml`). В **Run workflow** выберите ветку
PR. Запуски из `main` и тегов отклоняются. Оба APK собираются как отдельное
приложение **Argon Test** (`app.titaniumru.browser.test`) и подписываются
тем же постоянным релизным ключом, что и **Argon**. Releases не создаются;
тестовые APK скачиваются из Artifacts запуска. Предыдущий
`build-all-no-publish.yml` сохранён как отдельный прежний вариант.

| | Релизная сборка | Тестовая сборка |
| --- | --- | --- |
| Ручной workflow | `build-all.yml` | `build-test-branch.yml` |
| Исходники | `main` | Точный SHA выбранной временной ветки PR |
| Имя приложения | Argon | Argon Test |
| applicationId | `app.titaniumru.browser` | `app.titaniumru.browser.test` |
| Подпись | Постоянный ключ Argon | Тот же постоянный ключ Argon |
| Результат | APK в GitHub Releases | APK в Artifacts запуска без создания Release |
| Файлы APK | `Argon-…-release-…apk` | `Argon-Test-…-release-…apk` |

Сборки устанавливаются рядом и обновляют каждая свой пакет. Тестовый путь
сохраняет приложение с суффиксом `.test` независимо от типа подписи; выбор
релизного ключа не превращает его в production-пакет. Издатель дополнительно
отклоняет APK с `application_identity.variant=standalone-test`, даже если он
подписан релизным ключом. Полный релизный workflow закреплён за main и
релизной подписью.

### Совместная установка и обновления

- Chromium получает `manifest_package` из `chrome_public_manifest_package`.
  Authorities всех провайдеров формируются из него: например,
  `app.titaniumru.browser.FileProvider` и
  `app.titaniumru.browser.test.FileProvider`. Java FileProvider использует
  `Context.getPackageName()` и тот же суффикс. Это эквивалент привязки
  `${applicationId}` в Gradle; Argon собирается через GN/Jinja.
- У Test удаляются унаследованный Vanadium `original-package` и регистрация
  `googlechrome://`. Общий UID не используется. Пользовательские permissions,
  процессы и task affinity проверяются на принадлежность своему package.
  Обычные HTTP/HTTPS-фильтры сохраняются: Android видит два браузера и использует
  выбранный пользователем обработчик. Отдельных подтверждённых App Links нет.
- GCM/уведомления Chromium используют контекст текущего приложения; их
  PendingIntent и NotificationManager принадлежат своему пакету. В Argon нет
  `google-services.json` или подключённой конфигурации собственного Firebase-проекта;
  Google API-параметры в `args.gn` заданы заглушками. Отдельная Firebase-регистрация
  для `.test` потребуется при подключении такого проекта. Доставка удалённых
  push не считается подтверждённой проверкой манифеста.
- Новый тестовый запуск получает `versionCode = 1000000000 + github.run_number`
  служебного workflow. Повторные попытки сохраняют код и сертификат, новые
  запуски увеличивают код. Метаданные и отпечаток APK включают этот код.
- До доступа к релизному ключу и после подписи анализируется итоговый merged
  manifest через SDK `aapt2`: package, versionCode, все provider authorities,
  permissions, shared UID, legacy package aliases, URI-схемы, task affinity и
  процессы. Несоответствие останавливает сборку. Отчёт `manifest-identity.json`
  прикрепляется рядом с APK. Проверка закреплённых исходников отдельно сверяет
  package-привязку FileProvider, GCM и NotificationManager.

Ранее установленный Argon Test с временной подписью нельзя обновить APK с
постоянной подписью: для перехода потребуется однократно переустановить именно
Test, предварительно сохранив нужные данные. Последующие Test → Test используют
одинаковые applicationId и сертификат. Установка и обновление на реальном
Android-устройстве остаются обязательной проверкой перед выпуском.

GitHub привязывает запись Actions cache к ref запуска, а не к checkout.
Поэтому входной workflow передаёт номер своего запуска служебному
`build-test-main.yml`, выполняемому в `main`. Служебный workflow проверяет
источник, берёт точный SHA из исходного запуска и собирает этот SHA.
Изменение или удаление ветки после запуска не подменяет исходники.
Сводка входного запуска содержит ссылку на ход сборки и готовые APK в
**Artifacts** служебного запуска. Успех передачи задания ещё не означает
успех компиляции — её результат показан по этой ссылке.

Все часовые снимки, финальный `ccache` и автопродолжения принадлежат
`refs/heads/main`. Ключи версии Chromium, ревизии и ABI совпадают с полным
workflow, поэтому результаты тестирования накапливаются в main, а после
слияния используются обычной сборкой main. Тестовые и обычные сборки main
используют общую очередь, чтобы следующая сборка восстановила предыдущий
подтверждённый снимок. Новый исполнитель поддерживает очередь нескольких
тестовых запусков.

**Версия Chromium из выбранных исходников определяет актуальный кеш.** Если
версия или закреплённая ревизия изменились, в обоих конвейерах перед
восстановлением удаляются кеши других версий/ревизий этой ABI в main.
Это действует и при откате версии.
Снимки текущего Chromium продолжают накапливаться; другая ABI очищается своей
сборкой. Ошибка обязательной очистки останавливает сборку. Дополнительные
PR для прогрева кеша или переноса результатов после слияния не нужны.

Docker-образ тоже общий: `ghcr.io/loopfade/argon-build:branch-main`.
Оба конвейера используют один рецепт `docker/chromium/Dockerfile` и один
исполнитель `build-chromium-image.yml`, без отдельной копии для Test.
Служебный запуск проверяет его входы по точному SHA тестируемой ветки. При
совпадении образ переиспользуется, при изменении патчей или версии Chromium
один раз готовится новый образ с чтением кешированных слоёв предыдущего.
После успешной подготовки образ и встроенный BuildKit-кеш публикуются под
тем же `branch-main`. ARM и ARM64 получают один неизменяемый digest.
Сборка main после слияния переиспользует этот образ по совпадению входов,
даже если SHA merge-коммита отличается. Ошибка подготовки не заменяет
предыдущий образ. Старые версии удаляются после завершения потребителей;
используемые активными сборками и проверками digest сохраняются.

Однократно оба новых workflow, вспомогательный скрипт и обновлённые общие
исполнители подготовки образа и сборки APK должны попасть в main, чтобы GitHub
мог запустить служебную часть.
В дальнейшем достаточно создавать рабочие ветки с этими файлами, наполнять
один PR изменениями и повторять тестовый запуск по мере необходимости.

Параметры запуска:

| Параметр | Назначение |
| --- | --- |
| Подпись | В двух основных конвейерах всегда постоянный ключ Argon; выбор подписи оставлен только в прежнем `build-all-no-publish.yml` |
| `runner` | Linux x64 runner для компиляции, минимум 100 GiB свободного места |
| `auto_continue` | Продолжать тот же цикл после исчерпания времени runner; по умолчанию включено |

Новый цикл APK запускается только вручную; автопродолжение после тайм-аута
сохраняется. `validate.yml` выполняет проверки только в PR, направленных в
`main`, без сборки APK и публикации prepared image. Push и слияние не запускают
повторный прогон. Закрытие PR запускает только очистку его кешей.
Для обязательных проверок нет фильтра путей: каждый PR получает статусы,
включая изменения только документации или панели.
При несовпадении подготовленных
входов validation создаёт временный Chromium checkout внутри BuildKit;
проверяет полные GN-графы обеих ABI, цели JNI/Java/APK и нативные domain tests.
Результат не заменяет общий образ `branch-main`.
Прежние `build.yml` и `build-arch.yml` удалены. Подготовка образа, сборка
архитектуры и публикация доступны конвейеру через `workflow_call`.

В правилах защиты `main` должны быть обязательными две проверки GitHub Actions:
«Проверить исходники, патчи и поведение Argon» и «Проверить графы Android и
доменную политику». Требование актуальности ветки относительно `main` проверяет
совместимость с последними изменениями перед слиянием. Эти правила настраиваются
в GitHub отдельно: сам workflow с тестами не запрещает слияние.

Автоматические данные панели сохраняются в служебной ветке
`argon-dashboard-data`, создаваемой из `main` при первом обновлении. Публикация
Pages читает JSON из неё; до первого обновления используется снимок из `main`.
Бот панели не пишет в защищённую `main` и не требует исключения из правил.

## Как выбирается необходимая работа

1. Проверяются закреплённые входы обеих архитектур. Для release до дорогих
   этапов проверяются PKCS12, пароли, alias и действительность сертификата.
2. Для ARM64 и ARM независимо ищутся доступные артефакты предыдущих запусков
   обоих полных workflow. Совпасть должны коммит, архитектура, режим подписи,
   отпечаток подготовленных входов и release-сертификат. APK заново проверяется
   через SHA-256, apksigner, zipalign, aapt2 и проверку ABI. Проверенные файлы
   прикрепляются к текущему запуску с исходными сведениями о сборке.
3. Если оба APK переиспользованы, Docker и компиляция пропускаются. Иначе
   проверяется manifest/config образа `ghcr.io/loopfade/argon-build:branch-main`
   без скачивания слоёв Chromium. Метка `io.argon.prepared-inputs` содержит
   отпечаток исходников, патчей и рецепта подготовки. При совпадении используется
   существующий образ, при несовпадении выполняется Docker-сборка с BuildKit cache.
4. Полученный immutable digest один раз передаётся всем недостающим сборкам.
   ARM и ARM64 компилируются параллельно, если нужны обе архитектуры.
   При `TOOMANYREQUESTS` от GHCR скачивание повторяется до четырёх попыток
   с паузами 10/20/40 секунд и учётом `retry-after` до 60 секунд. Все попытки
   используют тот же digest; ошибки доступа, отсутствующий образ и заполненный
   диск сразу останавливают задачу. Такое же правило применяется в проверках.
5. Восстанавливается ccache своей версии/ревизии Chromium и архитектуры.
   Новая версия Chromium начинает отдельный чистый кеш. Изменения Argon внутри
   той же версии используют накопленные результаты.
6. Ninja запускается один раз и выполняет недостающие цели, включая JNI,
   Java и APK. Отдельного обязательного прогрева перед сборкой нет.
   Подпись, проверка APK и запись сведений о его происхождении выполняются
   внутри одного контейнера, чтобы работать с файлами от того же пользователя.
7. Для release существующий издатель проверяет оба APK и публикует релиз;
   повторная публикация тех же файлов использует его проверки идемпотентности.

В ARMv7 APK Chromium добавляет пустую `lib/arm64-v8a/libplaceholder.so`, чтобы
Android не показывал предупреждение об устаревшей ABI. Проверка архитектуры
допускает только эту пустую заглушку дополнительно к `armeabi-v7a`. Непустая
заглушка и любые другие библиотеки чужой ABI отклоняются; настоящие библиотеки
выбранной архитектуры остаются обязательными. ARM64 APK проверяется без этого
исключения. Флаг `enable_android_secondary_abi = false` не отключает заглушку.

Сводка запуска показывает, какие APK и образ переиспользованы. Сводка каждой
компилируемой архитектуры содержит результат и ключ восстановленного кеша;
журнал содержит статистику ccache.

Карта системных C++-модулей Android использует общий каталог заголовков NDK
и каталог только целевой архитектуры. Выбор принудительных `asm/*`-заголовков
не зависит от порядка обхода каталогов других архитектур. Исправление применяется
в слое патчей prepared-образа, сохраняя слой исходников, SDK и компилятора.
Ключ ccache не меняется: уже сохранённые результаты с такой же картой подходят,
а записи только с прежней картой потребуют однократной перекомпиляции.

Для исследования промахов есть ручной workflow **Проверка кеша компиляции ARM**.
Выбор `arm` или `arm64` восстанавливает отдельный кеш этой архитектуры для
версии и ревизии из текущего `build-lock.json`. Диагностика сравнивает хеши
зависимостей в манифестах и заголовки сохранённых Clang-модулей. Результаты
распаковываются во временные каталоги; workflow не сохраняет и не удаляет кеш.

## Сохранение прогресса и продолжение

Пока Ninja работает, приблизительно раз в час сохраняется отдельный снимок
ccache. Архивируется снимок, а компилятор продолжает работать со своим живым
каталогом кеша. Эти сохранения не прерывают Java-задачи или линковку.

После каждого часового ожидания checkpoint выводит подробную статистику
живого кеша через `ccache --show-stats --verbose`: попадания, промахи, размер,
ошибки и некешируемые вызовы. Счётчики накапливаются после сброса перед началом
сборки. Вывод выполняется и при завершении сборки до конца часа; ошибка
диагностической команды не блокирует сохранение снимка.

Перед шестичасовым дедлайном сборка контролируемо останавливается с резервом
30 минут на финальный снимок и загрузку артефактов; дополнительно оставляется
три минуты на остановку процессов. Незавершённые линковка и Java-задачи между
разными runner не сохраняются, поэтому они получают непрерывное время в каждой
попытке. Каталог `out` не переносится между runner.

Автопродолжение разрешается только после фактического исчерпания бюджета и
подтверждения нового непустого снимка через GitHub API. Оно повторяет нужные
неуспешные архитектуры исходного запуска с прежним коммитом и digest образа.
Успешная архитектура повторно не собирается. Ошибки компиляции, подписи,
проверки происхождения и ранний OOM не запускают автопродолжение. Число
автоматических продолжений ограничено десятью.

Если `auto_continue` выключено, повторить незавершённую работу можно через
**Re-run failed jobs**: накопленный ccache восстановится. Отменённые пользователем
запуски автоматически не продолжаются.

Внутри одной версии и ревизии Chromium старые снимки удаляются после
подтверждённого сохранения нового. При переходе на новую версию перед
восстановлением отдельно удаляются кеши старых версий этой ABI в той же
ветке: они не подходят новому компилятору и освобождают место для прогресса
новой сборки. Кеши другой ABI, другой ветки и более новой версии сохраняются.
Старые версии prepared-образа очищаются после завершения потребителей;
активные сборки и проверки сохраняют используемые digest.

Первый запуск после перехода со старой схемы может обновить образ: старый
образ не содержит метки отпечатка. При этом существующий BuildKit cache и
ccache той же версии Chromium продолжают использоваться. APK старых workflow
без метаданных нового плана не считаются готовым результатом полного workflow.
