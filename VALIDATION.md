# CI-проверки Argon

Обычный CI проверяет регистрацию выхода и renderer guard в GN-графах ARM64/ARMv7,
совместимость патчей с закреплёнными Chromium/Vanadium и выполняет host-тесты
реальной Java-логики и C++ защиты загрузок. Длительность обычных заданий ограничена
30 и 60 минутами. Android-компиляция выполняется существующим ручным процессом
полной сборки с отдельным ccache для каждой архитектуры и сохранением прогресса;
в нём `argon_exit.o` включён в явный список обязательных целей.

Этот документ описывает текущую CI-схему Argon: проверку исходников и патчей,
подготовку Chromium, ручную релизную сборку двух Android ARM-архитектур,
автоматическое продолжение долгих jobs, публикацию Release и dashboard.

## Полный ручной цикл

Основная точка входа — **Сборка Argon (полный цикл)**
(`.github/workflows/build-all.yml`). Один **Run workflow** в `main` проверяет
готовые APK, при необходимости подготавливает образ и собирает недостающие
архитектуры. Компиляция непрерывная, с часовыми снимками ccache; release
публикуется после проверки обоих APK. [Параметры, правила переиспользования
и продолжения](docs/build-pipeline.md).

Прежние `build.yml` и `build-arch.yml` удалены вместе с их скриптом прогрева.
Полный цикл использует `build-unified-arch.yml` и не прерывает Ninja на
промежуточных сохранениях.

## Закреплённые входы

Актуальные версии и commit SHA задаются в `build-lock.json`:

- Chromium: `156.0.8078.47`, commit
  `1d17a2e2ee147bb7d6ae2ab6abdb3a2510c17775`;
- Titanium: `a3e4b86339a8db237d95d8e8e78248c8f6a1df68`;
- Vanadium: `2ae4335402eabcc6e025f3400185fe25094d8521`;
- BoringSSL: `2ea3200c3a3ec176613ab7a0b9a4ffc6db846120`;
- release revision: автоматически, отдельно для каждой версии Chromium.

Старое поле `argon_revision` в `build-lock.json` сохраняется для совместимости
с уже подготовленными образами и больше не задаёт номер релизного тега.
Вручную изменять его при выпуске не нужно.

`scripts/preflight.py` проверяет согласованность pins, Vanadium gitlink,
версии Chromium, сертификата, filter-list pins и GN-конфигурации.

## Проверка Argon и правил доверия сертификатам

Workflow `.github/workflows/validate.yml` запускается на push, pull request
и вручную. Изменения только dashboard-файлов и workflows его обновления/
публикации исключены и для push, и для pull request.

При закрытии PR запускается cleanup: удаляются Actions caches закрытых PR. На обычном push этот дополнительный
runner не создаётся. При закрытии PR основная validation job не выполняется.

Validation:

1. Выполняет preflight и генерирует GN args только для `arm64` (`arm64-v8a`)
   и `arm` (`armeabi-v7a`).
2. Запускает Python unittest suite.
3. Проверяет shell-синтаксис build/CI scripts.
4. Проверяет применение CA/JNI/About overlay к закреплённым upstream-исходникам
   и зависимость генерации иконок адресной строки на Android с отключённым VR.
   В той же проверке применяется патч общего периода удаления данных и
   запускаются Java-сценарии обоих окон с телами методов закреплённого Chromium.
   Проверяются сохранение выбора, отмена, переход, повторное открытие и
   идемпотентность. [Поведение и сопровождение патча](docs/browsing-data-period.md).
5. Собирает и запускает `scoped_ca_test` с закреплённым BoringSSL для
   production DNS/IP constraints.
6. В отдельной job генерирует полные Android GN-графы для ARM64 и ARMv7,
   проверяет наличие явных JNI, Java и APK-целей основного `build.sh`,
   затем собирает host target `argon_domain_policy_tests` и запускает
   `TitaniumRuDomainPolicyTest.*` и `ArgonRussianCaPolicyTest.*`
   с настоящими GURL, ICU и public/private PSL
   закреплённого Chromium. Prepared image предоставляет sources/toolchain;
   header и тесты берутся из проверяемого checkout, включая pull requests.

   При совпадении отпечатка подготовленных входов используется immutable digest
   общего образа. Если pins или Argon-патчи изменились, job выполняет target
   `domain-policy-tests` Dockerfile: подготавливает текущий checkout и запускает
   тесты непосредственно внутри BuildKit. Это позволяет проверить обновление
   Chromium в отдельной ветке до слияния. Результат остаётся в локальном build
   cache: экспорт и импорт второй копии Chromium в Docker daemon, публикация
   в GHCR и замена `branch-main` не выполняются. Проверка соответствия исходников
   и toolchain остаётся обязательной. На подготовку и тесты отведено до 60 минут,
   включая подготовку при отсутствии совместимого образа.

Проверка CA/JNI использует те же исключения патчей Vanadium, что и `build.sh`,
включая раннюю инициализацию внешнего config app. Python-тесты отдельно
проверяют выбор ветки DevTools до Chromium `156.0.8060.0` и на этой границе:
закреплённый Chromium 156 должен использовать новую ветку.

Эта стадия не собирает релизный APK. Конфигурация, подготовка Android-модулей
и release pipeline поддерживают только `arm64-v8a` и `armeabi-v7a`.

## Подготовленный Chromium image

Workflow `.github/workflows/build-chromium-image.yml` вызывается полным
ручным циклом через `workflow_call`. Отдельного ручного запуска и запуска
от push у него нет. Образ с совпадающим отпечатком входов переиспользуется.

Workflow подготавливает закреплённые Chromium sources/toolchain и публикует
OCI image в GHCR. Один совместимый prepared image используется обеими
ARM-сборками. Docker отдельно кэширует закреплённые исходники и toolchain,
Argon-патчи, затем проверки и GN. Изменения overlays переиспользуют слой
загрузки исходников; runtime CI и документация не переустанавливают патчи.
Commit SHA записывается в OCI label после тяжёлых слоёв. При очистке GHCR
оба места вызова проверяют все страницы активных сборок и публикаций и
сохраняют старые digests, пока они могут использоваться.

Подготовка образа возвращает зафиксированный digest непосредственно полному
workflow. Проверка необходимости опирается на фактический GHCR manifest/config
и отпечаток подготовленных входов; история успешных Actions runs не нужна.
Самостоятельный workflow подготовки образа не запускает APK-сборку.

## Build Argon: запуск, кеши и продолжение

Единственная точка запуска полной сборки — `build-all.yml`, вручную в `main`.
При запуске выбираются `runner`, `signing=release|test` и `auto_continue`.
Сначала проверяются закреплённые входы и release-ключ, затем готовые APK.
Проверенный результат может переиспользоваться отдельно для каждой архитектуры.
Если готовы оба APK, подготовка образа и компиляция пропускаются.

Недостающие ARM64 и ARM APK строятся параллельно через
`build-unified-arch.yml` из одного immutable digest подготовленного образа.
Для каждой архитектуры восстанавливается свой ccache версии/ревизии Chromium.
Новая версия Chromium начинает чистый кеш; повторные попытки продолжают
накопленную компиляцию. Смена Argon-патчей в той же версии не сбрасывает кеш.

Ninja работает одним непрерывным процессом. Приблизительно раз в час
сохраняется отдельный снимок живого ccache; Java и линковка не прерываются
промежуточным таймером. Перед шестичасовым лимитом оставляется 30 минут на
финальный снимок и артефакты плюс три минуты на остановку процессов.
В пределах одной версии и ревизии удаление старых снимков разрешается после
подтверждения нового через API. Кеши более старых версий Chromium удаляются
отдельно перед восстановлением, только для текущей ABI и ветки; кеши другой
ABI, ветки или более новой версии не затрагиваются.

`continue-build.yml` — используемый служебный controller. Он продолжает
исходный вручную запущенный цикл с тем же SHA, образом и областью кеша,
повторяя только архитектуры с подтверждённым финальным снимком и marker
`argon-continuation-<attempt>-<arch>`. Успешная архитектура повторно не строится.
Ошибки компиляции, подписи, ранний OOM и отмена не разрешают автоматический
retry. Разрешены до десяти автоматических продолжений; параметр
`auto_continue=false` отключает их. Каталог `out`, Java-результаты и
незавершённая линковка между runner не переносятся.

## Публикация релиза

`.github/workflows/publish-release.yml` является reusable
`workflow_call` и отдельно вручную не запускается.

Publisher вызывается внутри `Сборка Argon (полный цикл)` только если одновременно
выполнены условия:

- для обеих архитектур получены проверенные APK;
- исходная ветка — `main`;
- исходный event — ручной `workflow_dispatch`;
- выбран `signing=release`.

Ручной `signing=test` релиз не публикует; pull request не запускает APK-сборку.

Если `main` продвинулся во время сборки, безопасные изменения документации,
dashboard и его deployment metadata не делают проверенный APK устаревшим.
Изменения build/signing/release logic по-прежнему блокируют публикацию
старого build.

Publisher скачивает **оба** artifacts из одного `Сборка Argon` run и
проверяет:

- одинаковые source SHA и Chromium version;
- `arm64-v8a` / `arm64` для первой сборки;
- `armeabi-v7a` / `arm` для второй;
- release signing;
- SHA-256 APK и checksum files;
- ожидаемые имена APK;
- идентичность Chromium, Ruthenium и Titanium license payload между
  архитектурами.

Публичный релиз содержит семь assets: два APK, две SHA-256 checksum и три
license files. Tag имеет формат `v<chromium_version>-<release_revision>`.
Release notes формируются **только на русском языке**.

Номер выбирается автоматически непосредственно перед публикацией под общим
concurrency lock `publish-release`. Для новой версии Chromium это `-1`, далее
берётся максимальный занятый номер этой версии плюс один. Publisher читает
все страницы тегов и релизов, включая drafts и теги незавершённых публикаций.
Теги других версий и upstream-теги без суффикса не влияют на счётчик.
Повтор публикации того же source SHA переиспользует его номер и заново
проверяет tag и все assets; он не создаёт новый релиз и не перезаписывает APK.
Ошибка чтения истории или несогласованные tag/Release останавливают публикацию.
Нумерация не меняет Docker inputs и не требует пересборки prepared image.

Перед изменением существующего Release publisher сверяет SHA-256 каждого
уже опубликованного APK, checksum и license file с проверенными artifacts.
Допускается только отсутствие всей ARMv7-пары в старом ARM64-релизе. После
добавления пары все семь assets повторно проверяются до обновления notes.
Неполные пары, лишние assets и дубликаты блокируют изменение Release.

Если для одной из архитектур отсутствует проверенный APK, publisher не
запускается и публичный релиз не создаётся.

## Dashboard и GitHub Pages

Статический dashboard доступен по
[https://loopfade.github.io/argon/](https://loopfade.github.io/argon/).

Исходники сайта находятся прямо в `main`:

- `index.html` — UI;
- `dashboard-data.json` — read-only snapshot;
- `.nojekyll` — публикация без Jekyll.

Workflow `.github/workflows/update-dashboard.yml` запускается после
завершения `Сборка Argon`, при изменении самого updater workflow и вручную.
При автоматическом запуске от `Сборка Argon` snapshot изменяется только если
завершившийся run соответствует опубликованному Release. В snapshot
сохраняются до трёх последних валидных опубликованных релизных билдов с jobs,
step timings, artifacts и release metadata. Snapshot включает все попытки
исходного run, в том числе неудачные прогревы. Wall time считается от старта
первой попытки до завершения сборки/публикации, включая ожидание retries;
время архитектуры суммирует её jobs без ожидания. Параллельные ARM jobs
не складываются в wall time. Таймлайн показывает отдельные попытки с паузами,
а детали архитектуры сохраняют шаги каждого прогрева.

Push с меткой `[history-only]` сохраняет опубликованный snapshot: свёртка
истории не создаёт новый релиз и не должна добавлять служебный коммит со
сменой timestamp над завершающим слиянием. Ручное обновление и обновление
после опубликованного релиза продолжают работать.

Updater проверяет связь завершившегося run с новым релизом до загрузки jobs.
Если payload совпадает с сохранённым snapshot без учёта `generated_at`,
файл и его timestamp остаются прежними. Та же проверка выполняется по
актуальному `main` перед записью, чтобы не создавать лишний commit/deployment.

После записи `dashboard-data.json` updater явно запускает
`Публикация панели Argon`. Это необходимо, потому что commit, созданный
через `GITHUB_TOKEN`, не используется для рекурсивного запуска push-workflow.

Workflow `.github/workflows/deploy-dashboard.yml` публикует
`index.html`, `dashboard-data.json` и `.nojekyll` через официальный
GitHub Pages deployment из `main`. Браузер не обращается к GitHub API и
не получает токены.

Dashboard является read-only: он не может запускать, перезапускать или
отменять сборки. Активный ещё не опубликованный `Сборка Argon` следует
смотреть непосредственно в GitHub Actions.

## Что CI не подтверждает автоматически

CI не заменяет проверки на реальном Android-устройстве. Отдельно при
необходимости проверяются:

- установка и запуск APK;
- UI настроек сертификатов и расширений;
- end-to-end TLS-сценарии;
- публикация через магазин приложений.

Публичные APK выпускаются только для `arm64-v8a` и `armeabi-v7a`.

## Что запускается при изменениях

- Prepared Chromium inputs → validation проверяет текущий checkout; при
  несовпадении общего образа выполняет временную подготовку внутри BuildKit.
  Публикация нового prepared image происходит при следующем ручном запуске.
- Push в `main` → **не запускает релизный `Сборка Argon`**.
- `Сборка Argon (полный цикл)` в `main` → запускается только вручную.
- Pull request → обычная validation; сборка APK автоматически не запускается.
- `README.md` и `VALIDATION.md` → выполняется обычная validation, без APK
  и публикации prepared image. Совместимый общий образ переиспользуется;
  при его отсутствии validation выполняет временную подготовку checkout.
- Dashboard-only файлы и workflows snapshot/deploy → не запускают
  `Сборка Argon`; изменения snapshot/site публикуют только dashboard.
